# Build `#build=kaiyo-sales` through a data engineer's eyes

Review, 2026-11-20 (Opus, read-only). The question: when the owner shows the build to a mentor, what in it is right by data-engineering and analytics-engineering practice, what is simplified and said honestly, and what is wrong or misleading. Inputs: the code at `463375e`, `docs/build-kaiyo-sales-spec.md`, Gemini's junior walk `../shots/gemini/2026-11-20/build-walk.md` (only its five points of substance; screen bugs are lab-build-fixes' job), and three DuckDB 1.5.6 queries on `public/datasets/quaera/staging_raw_sellout.parquet` run for this review. Code is cited as `file:line`; "spec" is the build spec.

**Short verdict.** The spine is sound and better than most tutorials: raw files read as text, every clean table rebuilt from bronze through a replayable list of steps (idempotent by construction), checks that return 0, link checks for type, uniqueness and orphans, a reconciliation question (A4), and a Refresh that fails loudly on a new date spelling. Two things a data engineer will catch: **returns carry positive revenue** while the screen says "a return stays negative", and **key checks run only once, at design time**, not on every Refresh. The rest is naming and honest one-liners.

## 2. Gemini's five points

**2.1 Quick look "before cleaning" already cleans. Decision: say it honestly (S).** A truly raw look cannot give a revenue sum (text, decimal commas), so the parsing has to happen; the problem is only the word "anything". The numbers are deliberately the "nothing done" row of spec section 7 (duplicates and stale stores still in), so keep the SQL. New `QUICK_LOOK_TEXT.lead`: "All four files are in. A first look at the sales before the real fixes: Lab read the dates, commas and names the quick way (the SQL is below), but the copies and the stale customers are still in. Two numbers for the Head of Sales." The `clean_*` names in the sidebar right after Connect come from the given step (spec 2.5, last line): fine, as Power Query adds Changed Type.

**2.2 `R-01` to a number. Decision: keep, add one line (S).** `region_id` is a natural key, not a surrogate, and the system of record (`dim_region`, `customers.csv`) uses integers, so conforming the file to it is the usual move; P7 lives in Clean, which is the staging place Gemini asks for. Line for the P7 pass (`linkData.ts:96-99`): "R-03 and 3 are one key written two ways. We made the file match customers; turning customers into text would work too. What matters is one type on both sides." Extract number would mis-read a code like `R-03B`; not worth a change for 16 fixed codes.

**2.3 Unknown store in July passes green. Decision: Gemini's example is wrong, the gap is real; add tests to the journal (S-M), no Unknown member, no quarantine.** `Konbini 24 Store #1055` is customer 55 in `dim_customer` (traditional, `chain_name` NULL, checked); July picks stores only from `ref_sales` (`buildRun.ts:54`), so every July name finds its customer and `customer_id` is not NULL. What Gemini saw is the no-chain store leaving the chain bars, which A4/A5 teach on purpose (tile SQL filters `chain_name IS NOT NULL`, `kaiyoSales.ts:395`). The real gap: the fact is a `LEFT JOIN` (`buildLinks.ts:293-294`), Refresh never re-runs the L1/L2 orphan checks, so a truly new store would vanish from every chain or region view while the KPI keeps it, with a green journal. In the scale of this build:
- **Do**: after "Build gold_fact_sales", journal lines "Test: every sale finds a customer / a product / each customer once" with the orphan and uniqueness SQL that `checkSqlText` already writes (`buildLinks.ts:304-329`); 0 = ok, otherwise **warning** with the count and one sample name. Label them "the dbt tests relationships and unique" in the note.
- **Not now**: Unknown member (`customer_id = -1`, Kimball) needs a seeded row in every dimension and changes every tile; quarantine tables need a second output and UI. Mention both in one sentence on the warning: "In a warehouse such rows go to an Unknown customer or to a quarantine table."
- **Later, with variants**: put one new store in the July of a variant so the warning actually fires.

**2.4 K1 template, then K2 to K5 almost empty. Decision: change the start text (S).** Keep free SQL (that is the point of More), give the shape: K2 `start` (`kaiyoSales.ts:604`) becomes the FROM and JOIN lines with blanks (`FROM build_kaiyo.gold_fact_sales f JOIN build_kaiyo.gold_dim_product p ON p.product_id = f.____`, then `-- GROUP BY … ORDER BY …`); K3 to K5 a comment listing the tables and the join key (`-- gold_fact_sales f, gold_dim_customer c on customer_id`). K3 already accepts 217 and −217 (`unsigned: true`); its question could say "how many units (as a positive number)".

**2.5 P2 `ROW_NUMBER` as the drop-out point. Decision: presentation, not order (S, M for the optional part).** P2 must stay early: the copies are what change the headline (Nagisa first instead of Minori, spec 1), and P3 builds on it ("you wrote this in P2"). The blank is only a column list; what scares is reading the window. Fixes: show the two copies of one sale above the blank (same date, store, SKU; only `raw_id` differs) and a two-row picture of `copy_no` 1 and 2; the full-width blank is in v0.48.0's left column already. Optional (M): ticks on the three column headers that write the `PARTITION BY` list, like Power Query's "Remove duplicates" on selected columns, with the SQL shown.

## 4. Edge cases of the data: caught or not

| Case | Where | Caught? |
|---|---|---|
| Same file twice (a copy in the folder) | pattern mode reads it; P2's key has no `source_file`, so the copies drop | Yes, silently: only the row counts show it |
| Run pressed twice | `CREATE OR REPLACE` from bronze | Yes: same result |
| New date spelling | date step [Error], star and tiles "Not run" (`buildRefresh.ts:106-111`) | Yes, loudly (the R1 lesson) |
| File of another shape (`,` delimiter, other columns) | one `read_csv` over all files (`kaiyoSales.ts:113-114`), no `union_by_name` | Expected: the bronze line errors, later stages skip (`:61`, `:67-71`); not tested |
| Empty file, header only | reads 0 rows | No warning; a missing month looks the same as a quiet one |
| Unknown store or SKU | fact `LEFT JOIN`, NULL id | **No** (§2.3) |
| Future date (2027 in a July file) | parsed, becomes a new point on the line | No; dbt `accepted_range` would |
| Negative units | P8 info | Shown, kept; revenue sign contradicts (§1, Returns) |
| NULL revenue / units | P8 info; `count(revenue)` trap in K1 | Yes, taught |

## 5. What the owner can say to the mentor

- "Every clean table is rebuilt from the raw files by a list of steps, so the whole chain is replayable and idempotent; that is the dbt idea in Power Query clothes."
- "The checks are the usual tests, unique, not null, relationships and a reconciliation of the bars against the total; in the build they gate each step, and the Refresh is where I am adding them to every run."
- "It is a full refresh run by hand in the browser, on purpose: at 3,000 rows the lesson is that steps written once survive a new file. Incremental loads, scheduling and an orchestrator are named on the screen, not simulated."
- "The star keeps the source ids and Type 1 customers to stay small; surrogate keys, an Unknown member and Type 2 history are the next layer, and I know where they would go."

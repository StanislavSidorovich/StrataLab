**Row limit.** A run brings at most **10,000 rows** of its result into the page. DuckDB streams the result (`conn.send(sql, true)`) and the page stops reading one batch past the limit, so the rest is never made: `SELECT *` over 5 million rows now takes ~30 ms and the memory of 10,000 rows, instead of holding all of them twice (DuckDB's copy and the grid's) and stalling the tab. When there was more, the count reads **10,000+ rows** and a note over the grid says so, with **Up to 100,000** and **Up to 1,000,000** (then **All rows**): a query that only reads runs again with that limit; a script that changes data is not run again by itself (its changes would happen twice), and the note says the next Run of the tab uses the higher limit instead. Export ▾ says it takes the rows shown; Messages and History read “10,000+ rows (first 10,000 shown)”. PostgreSQL tabs get the same limit on the grid (PGlite hands over the whole result at once, so it spares the page, not the engine). Rules in `src/core/rowLimit.ts`, the streaming in `src/db/engine.ts` (`queryLimited`).

## Decisions

- ✱ **Walkthroughs open without running.** They are for learning step by step (Shift+Enter), and the first run downloads Python; the short guide examples, by contrast, run in one click. Only the last DataFrame of a run goes to Table (as before for the grid): the Open in Table button sits at that output only.

- ✱ **Dataset guides live in a dialog, opened from the catalog card and the folder menu** (owner chose this over a side panel, 2026-10-19). Examples pair SQL and pandas on the same question, so switching the language compares them; Run opens a new tab rather than writing into the user's tab. The cheat sheet is made from a small spec per dataset (`cheatSheet` in `src/data/guides.ts`: a table, a number, a group column, a column with NULLs, a table to join), so all five stay alike and are tested the same way.

- ✱ **Python: its own worker, not the sqlglot one** (stage 7). Both load the same Pyodide files (downloaded once, kept by the service worker), but the user's Python runs code that can loop forever, and the only way to stop a worker's Python without cross-origin isolation (GitHub Pages can't send COOP / COEP headers) is to end the worker: the T-SQL translator must not die with it, and user code must not see or overwrite sqlglot's globals. The cost is a second Python's memory (~40 MB) when a T-SQL tab and a Python tab are both used in one visit.
- ✱ **One Python session for all Python tabs**, variables kept between runs until **Restart Python**, as one Jupyter kernel per notebook would be per tab: one session costs one Python's memory, and a student's tabs usually belong to one piece of work. **Stop** = restart (see above), and says so.
- ✱ **Tables reach pandas as columns, not as Arrow / Parquet / CSV.** DuckDB gives the page an Arrow table; the page sends each column as a typed array (numbers, dates as epoch milliseconds, booleans) or a list of strings, with a null mask, and Python builds the DataFrame with `numpy.frombuffer` (`src/core/pyTransfer.ts`, `lab.py`). Arrow IPC or Parquet would need pyarrow in Pyodide (10 MB more, the size of pandas itself); CSV loses the types (dates, NULL vs empty text, leading zeros). Types: integers → int64, or pandas' nullable `Int64` when there are NULLs; DECIMAL and floats → float64; dates and timestamps → `datetime64`; booleans → bool / `boolean`; text → strings; anything else (lists, structs, intervals, blobs) → its text. Back (`lab.save`, a DataFrame in the grid) the same way the other direction, into an Arrow table that DuckDB inserts (`insertArrowTable`, as Save as table does).
- ✱ **`lab.table("…")` reads what the code names, before the cell runs.** A worker can't wait for the page synchronously without SharedArrayBuffer (again cross-origin isolation). So before a cell runs, the page finds `lab.table("…")` and `lab.sql("…")` calls with a written string (`src/core/pyCells.ts`), runs them in DuckDB and sends the results along; inside the cell the calls return at once. Names built at run time (`lab.table(name)`) are fetched during the run where the browser can suspend WebAssembly (JSPI: Chrome and Edge 137+), and elsewhere (Safari, older browsers) fail with a message that says to write the name in the call. A `lab` that is a plain module (not `%sql` magics): it reads as Python, completes, and runs unchanged in Jupyter with the notebook's setup cell.
- ✱ **Pyodide's own builds of the packages, served with the site** under `pyodide/`, next to Pyodide's core: `npm run python-packages` (`scripts/fetch-python-packages.mjs`, run by the deploy like `npm run extensions`) takes pandas, matplotlib and their dependencies named in `pyodide-lock.json` from the Pyodide release on jsDelivr (or from the release archive on GitHub, `--from`), checks each against the lock's sha256, and adds seaborn's wheel from PyPI (pure Python, pinned by its hash: seaborn is not in Pyodide's build). Not committed to git (17.8 MB of binaries, like the DuckDB extensions). Without them (a dev checkout) the worker takes the packages from jsDelivr. **Left out:** scipy (14 MB; seaborn's KDE has its own fallback), pyarrow (10 MB, see above), statsmodels, scikit-learn: an open question for the owner. **Budget:** ≤ 35 MB for Python with all four packages on a first use, cached after; pandas alone ≈ 21 MB; matplotlib and seaborn only download when the code imports them (`loadPackagesFromImports`).
- ✱ **Python's packages are kept for offline after its first use, all of them**: once a Python session is up, the page fetches the served packages it hasn't used yet (matplotlib, seaborn: 9.8 MB) in the background, so the service worker keeps them, rather than only what that first session happened to import. A student who computed with pandas at home can still plot on a train. The cost is those 9.8 MB for someone who never plots; a setting could turn it off if the owner prefers (open question).
- ✱ **Output as Jupyter's**: per cell, `stream` (print), `execute_result` (the last line's value), `display_data` (figures) and `error`, each a MIME bundle (`text/plain`, `image/png`, `text/html` for DataFrames). The same shape goes into an .ipynb unchanged. Lab shows text and images, never the HTML (no markup from code into the page). The last DataFrame shown also goes to the grid as an Arrow table, so Chart, Export and Save as table work on it; matplotlib draws with Agg, every open figure becomes a PNG after its cell and is closed.
- ✱ **Python is a language on the tab's switch, cells are `# %%` lines in one editor**, not a separate list of cell editors: the tabs, File → Open / Save, history, the editor toolbar and the result pane stay one design for SQL and Python, it works on a phone, and `# %%` is what VS Code, Spyder, PyCharm and Jupytext read as cells, so a saved `.py` opens as a notebook there too. Run runs all cells (outputs shown per cell, `[1]`, `[2]` …), Shift+Enter the cell at the cursor.
- ✱ **.ipynb mapping**: nbformat 4.5; a `# %%` cell ↔ a code cell, `# %% [markdown]` with its lines as `# …` comments ↔ a markdown cell; outputs of the last run go to their cells with execution counts; the first cell, tagged `quaera-lab-setup`, defines `lab` with DuckDB (catalog datasets from `https://lab.quaera.app/datasets/…`, the user's own tables from `<name>.parquet`), so the notebook runs in Jupyter and Colab; Open drops that cell and keeps code and markdown (outputs and raw cells are not taken back in). Python tabs stay out of `#s=` share links, so the link format does not change.

- ✱ **Colours as in StrataSQL, not a theme list** (owner asked for model.quaera.app's way, 2026-10-17): two colours (editor, panels) per theme from StrataSQL's own tints plus any colour, rather than named themes (Solarized, Nord…): it matches the sister app, and a learner who wants a calmer screen picks one swatch. No text size here (StrataSQL has one): the browser's zoom does it, and the grid and editor would need checking at every size. The light / dark switch moved into the panel so the phone header keeps one button.
- ✱ **Explain runs only queries that read** (EXPLAIN ANALYZE), and only plans the rest: ANALYZE executes the statement, and a learner pressing Explain on a DELETE should not lose rows. Running a write inside a rolled-back transaction would give real numbers, but a crash or a stop between the two would leave the change. **The last statement only**, as Run shows the last result; the note says the ones before were not run. **A Plan view under the editor**, not a dialog: the plan and the query stay visible together, as in SSMS's Execution plan tab. **A tree of rows, not boxes and arrows**: it reads on a phone and needs no layout library; DuckDB's own text drawing is too wide for 390 px.
- ✱ **Charts drawn by our own SVG code, not a chart library**: three chart types need axes, bars, lines and dots, about 400 lines; a library (Recharts, ECharts, Chart.js) would add 50–300 KB and its own theming, and PNG export from SVG needs nothing extra. No new licence to list. **A Chart view next to Result** (as Azure Data Studio's Chart tab), not a panel beside the grid: the grid keeps its width on a phone.
- ✱ **History is a third view under the editor, not a side panel** (as Azure Data Studio's Query History pane): the sidebar is the database tree and a phone has no room for another panel. Clicking an entry opens a new tab and does not run it: the query may write or be slow, and the user's current tab is not overwritten. Kept in localStorage, not in DuckDB: it must survive a database restore, and a full storage keeps the newer half.

- ✱ **A File menu instead of Open / Save / Share buttons** (owner asked for “File with open, save… as in programs”): one place for files, data in and out and the whole database, and it fits a 390 px header. Ctrl+O / Ctrl+S stay.
- ✱ **Run / Stop above the editor, left of the dialect switch** (Azure Data Studio's place; owner agreed to move it): it runs this tab, in this tab's dialect.
- ✱ **DuckDB extensions downloaded at build time, not committed**: binary files tied to one DuckDB version; the deploy fetches the ones for the DuckDB it ships. If extensions.duckdb.org is down at deploy time, the deploy fails rather than shipping a site that silently depends on it. All or nothing per build: with one file missing the app keeps the default repository.

- ✱ **Engine: DuckDB-WASM** (MIT) rather than SQLite (too weak) or PGlite (kept for stage 4 as a dialect). Reads CSV/Parquet/JSON natively, fast on millions of rows.
- ✱ **No server.** Static site on GitHub Pages; the user's data never leaves the browser (no GDPR question, zero hosting cost).
- ✱ **OPFS registered by hand** (`src/db/engine.ts`): DuckDB-WASM 1.33's own `opfs://` path never registers a new, empty database file (it checks `getSize()`), so everything silently stayed in memory while the UI said “saved”. We create both files (`.duckdb`, `.wal`) and register them under plain names. A second tab cannot lock the same file, so it falls back to an in-memory database and the badge says so.
- ✱ **Excel via SheetJS CE 0.20.3** from cdn.sheetjs.com (the npm `xlsx` package is stuck on a vulnerable 0.18). Sheets are written to CSV with ISO dates, then DuckDB sniffs the types, so CSV and Excel go through one path.
- ✱ **Detection before DuckDB's sniffer** (`src/core/sniff.ts`): Windows-1251 fallback when the file is not valid UTF-8, `;` delimiter, decimal comma, `dd.mm.yyyy` dates. DuckDB can't do encodings and needs `decimal_separator` / `dateformat` to be told.
- ✱ **F5 runs the query** (SSMS habit) anywhere on the page, instead of reloading it.
- ✱ **T-SQL hints, not silent rewriting** (`src/core/dialect.ts`): when a query fails, SQL Server habits (`TOP`, `[brackets]`, `ISNULL`, `GETDATE()`, `GO`…) get a “use this instead” note. Seeing the difference is part of learning.
- ✱ **English UI**, like StrataSQL and StrataFlow (international students); RU/PT in stage 6.
- ✱ **Demo shop on first visit** (4 tables, fixed seed) so the welcome query works before any file is dropped.
- ✱ **`#ddl=` packing = StrataSQL's share links** (UTF-8 → deflate-raw → base64url, no padding), via the browser's own CompressionStream: no library, and one format across the Quaera apps. A link that inflates past 5 MB is refused (read chunk by chunk, so a crafted link can't fill the memory).
- ✱ **Foreign keys folded into CREATE TABLE** (`src/core/ddlPlan.ts`): StrataSQL (like pg_dump) adds FKs with `ALTER TABLE … ADD CONSTRAINT`, which DuckDB doesn't support. The plan moves each FK into its table and orders tables so referenced ones come first; a circle of tables loses the FK that closes it, with a note. Self-references are kept.
- ✱ **Translate what is safe, report the rest**: `public.` dropped, `serial` → integer NOT NULL, `GENERATED … AS IDENTITY`, `ON DELETE CASCADE / SET NULL`, `DEFERRABLE` and storage options left out with a note; names that are keywords only in DuckDB (`at`, `map`, `pivot`…) quoted; `DROP TABLE` never run (we ask instead). If DuckDB still rejects a table, it is retried without its FKs, then without its CHECKs, and the dialog says which.
- ✱ **Ask before replacing**: replace all / keep the existing ones and create the rest / cancel. Drops go in reverse creation order; a table another (non-model) table still refers to is kept, with a note.
- ✱ **No demo shop when arriving with a model**: whoever came from model.quaera.app came for that model, and the demo's `customers` / `orders` could clash with it.
- ✱ **One StrataLab tab**: StrataSQL's link opens a named window (`stratalab`), and StrataLab also reads `#ddl=` on `hashchange`, so a second click lands in the same tab (a second tab could not lock the saved database and would fall back to memory).
- ✱ **We download DuckDB's .wasm ourselves** (`src/db/engine.ts`) and hand DuckDB a `blob:` URL, counting bytes on the way. DuckDB's own progress callback only fires when chunks arrive more than 20 ms apart, so on a decent connection it stays silent. The file comes gzip-compressed, so Content-Length is useless for a percentage; `vite.config.ts` puts the unpacked sizes of both .wasm builds into the bundle at build time (`__DUCKDB_WASM_BYTES__`). The bar stops at 99% until the engine has started.
- ✱ **Check everything, then insert** (stage 2b, `src/core/fill.ts`): the file is copied into a temp table and each rule is one SQL query over a view that casts every column to the table's type, so a big file is checked by DuckDB, not row by row in JavaScript. The report lists rows by the number the user sees in the file.
- ✱ **Insert the good rows, skip the bad ones** rather than all-or-nothing (SSMS's import fails as a whole): the button says how many go in and how many are left out. Of two rows with the same key, the first is kept.
- ✱ **A file named like an empty table fills it** (a modelled table waiting for data); a table with rows is only filled when chosen (dropped onto, menu, or the dialog's select).
- ✱ **No silent rounding**: a fractional number going into an integer column is a problem. A decimal-comma file whose number column became text (one stray value) is still read with the comma, spaces as thousands separators.
- ✱ **One schema per dataset** (`chinook.Track`): datasets never clash with each other (Chinook and Sakila both have `customer`) or with the user's tables, and `schema.table` reads like SQL Server's `dbo.`. The user's own tables stay in `main`, unqualified.
- ✱ **Datasets served with the site** (GitHub Pages, `public/datasets/`), not a separate CDN: 2.3 MB of Parquet, same origin, no CORS question. **Original table and column names** kept (Chinook's PascalCase, Northwind's `"Order Details"`) so tutorials' queries carry over.
- ✱ **Built offline by `scripts/build-datasets.py`** with the browser's DuckDB version (1.5.4): Northwind from Microsoft's T-SQL script (m/d/yyyy dates → DATE, money → DECIMAL(10,2) checked for lost cents, pictures left out), Chinook / Sakila / Quaera from SQLite (Quaera's ISO-text dates → DATE). Sakila's `store.manager_staff_id` FK is left out: it closes a circle with `staff.store_id`, and DuckDB can't add a key later.
- ✱ **Self-referencing tables load in rounds** (bosses first): DuckDB checks a foreign key against rows already in the table, not rows of the same INSERT.
- ✱ **A dataset load is not one transaction**: after a dataset was dropped from a reopened file, DuckDB 1.5 refuses to commit several CREATE TABLEs with foreign keys together (“subject … has been deleted”). One statement at a time works; a failed load drops its schema again.
- ✱ **WAL emptied on start, CHECKPOINT after every query** (`src/db/engine.ts`), see “Where we are”. A crash between a write and its checkpoint loses that one write; a stale WAL lost the whole database.
- ✱ **AdventureWorks = AdventureWorksLT** (the `SalesLT` schema, 10 tables), not the full OLTP database (~70 tables in 5 schemas, 20+ MB): it is the one Azure SQL and most short tutorials use, and it fits the catalog's size. Built from Microsoft's own `AdventureWorksLT2022.bak` restored into SQL Server (any instance reachable by `sqlcmd`; Docker works), read back with `FOR JSON` as text and cached in `data-local/datasets-src/adventureworkslt/`, so later builds need no server. The OLTP CSVs were the other route, but they hold the full database, not LT's rows.
- ✱ **AdventureWorks types**: money → DECIMAL(19,4) (416 of 542 unit prices have 3–4 decimals, so (10,2) would lose them); `OrderDate`, `DueDate`, `ShipDate`, `SellStartDate`, `SellEndDate`, `DiscontinuedDate` → DATE (never a time of day, checked by the build); `ModifiedDate` → TIMESTAMP (some have one); `uniqueidentifier` → UUID; `tinyint` → SMALLINT; `bit` → BOOLEAN; the `xml` column as text; `ThumbNailPhoto` left out; the three views left out (one parses XML, one is a recursive CTE that is a good exercise to write).
- ✱ **Computed columns stored as values** (`LineTotal`, `SalesOrderNumber`, `TotalDue`): DuckDB's generated columns can't be filled by `INSERT … BY NAME` and would surprise the fill and DDL features; the values are SQL Server's own. `ON DELETE CASCADE` (order lines) left out, like StrataSQL's models.
- ✱ **Defaults that need nothing extra**: `rowguid` defaults to `uuid()`, `ModifiedDate` to `CAST(now() AS TIMESTAMP)`, `OrderDate` to today via `now()`, so an INSERT can leave them out as in SQL Server. `localtimestamp` and `current_date` were avoided: in DuckDB-WASM they first download the ICU extension.
- ✱ **Kept as in the source**: the Arabic, Hebrew, Thai and Chinese product descriptions are question marks in Microsoft's backup itself (508 of 762); they are not repaired, the card says so.

## Known gaps

- Python tabs (stage 7): Python can't be interrupted, only restarted (Stop): a long loop loses the session's variables. `lab.save` writes when its cell ends, so a `lab.sql` later in the same cell doesn't see the new table (the next cell does). A table named at run time (`lab.table(name)`) needs Chrome or Edge (JSPI); Safari and Firefox need the name written in the call. Only pandas, numpy, matplotlib, seaborn and the standard library: no `pip install`, no scipy (seaborn's KDE works without it; `scipy.stats` doesn't). The grid shows at most 10,000 rows of a DataFrame (Export takes those rows; `lab.save` takes all). HTML outputs (styled DataFrames) show as text. One Python session for every Python tab. Not tried: Safari, Firefox, a real phone, and the real `#ds=quaera` load in this session (Parquet's DuckDB extension is blocked here: the Kaiyo tables were loaded from CSV copies for the check).

- Only Parquet and ICU are served with the site; any other extension a query autoloads (`spatial`, `httpfs`…) is still fetched from extensions.duckdb.org, and with the site's repository set it is looked for on the site first and fails. Add it to `OWN_EXTENSIONS` when a feature needs one.

- Numbers with a space as thousands separator (`1 234,50`) stay text: DuckDB has no thousands option. Could be cleaned before import.
- A result cut at the row limit exports only the rows shown; exporting every row of a big query needs `COPY (…) TO` in SQL (a “Export all rows” that runs the query through COPY is a candidate). PostgreSQL tabs still make the whole result before the grid is limited.
- Cloudflare Web Analytics is told the page address; whether its beacon includes the part after # (share links carry queries there; the app clears it once read) was not checked from this session.
- A multi-statement script in a DuckDB tab runs its statements before the last in one go: Stop only interrupts the last one. Running DuckDB tabs statement by statement needs a splitter (DuckDB-WASM's `extractStatements` is a candidate).
- PostgreSQL tabs have no Stop (PGlite can't cancel a query).
- The database backup has DuckDB's tables only; PostgreSQL's (PGlite) are not in it.
- A tab opened from a .sql file forgets the file on reload: the next Save asks where to save again.
- T-SQL that has no DuckDB counterpart is passed on and fails in DuckDB with DuckDB's error: variables (`DECLARE @x`), `MERGE … OUTPUT inserted.…`, `BEGIN TRY … END CATCH`. The translation view says so where sqlglot warns; `EXEC` (stored procedures) is stopped before running with a note. `SELECT … INTO #tmp` works (a temporary table).
- `'text' + column` is turned into `||` only when one side is a string literal (or already a `||`): `first_name + last_name` stays `+` and fails in DuckDB with the T-SQL hint. sqlglot doesn't know column types.
- The PostgreSQL database is one per browser (IndexedDB) and not locked: two tabs of Quaera Lab writing to PostgreSQL at once could overwrite each other's changes. PostgreSQL's data is separate from DuckDB's: a change in one is not seen in the other until copied again (the copy replaces).
- Copying to PostgreSQL: `LIST` / `STRUCT` / `MAP` columns go as text; DuckDB CHECKs PostgreSQL rejects are left out with a note (none in the catalog datasets were seen to fail, but not all were tried, see above).
- Not tried yet on Safari / Firefox (OPFS sync access handles are supported there, but untested).
- `#ddl=` opened while StrataLab is already open in a tab **not** started from StrataSQL's link (typed address, bookmark) opens a second tab, which gets an in-memory database (the badge says so).
- “Show as model” sends the current state of the tables: the model is a new copy in StrataSQL, not linked back (edits there don't come back to StrataLab; StrataSQL's “Open in StrataLab ↗” does that way).
- DuckDB foreign keys only block: `ON DELETE CASCADE / SET NULL` from a model are left out (noted in the dialog).
- Mobile: usable to look, not to work (sidebar hidden below 768 px; the catalog has a header button).
- Filling and generating work in My tables and the user's own datasets, not in a sample dataset's tables.
- A model from model.quaera.app (`#ddl=`) always lands in My tables; “into a new dataset named after the model” would need a change in StrataSQL too.
- Moving a table doesn't rewrite views that name it unqualified or from another schema (`SELECT * FROM orders` in My tables after `orders` moved to `sales`); renaming a dataset does rewrite views that name it.
- Tables and views only: macros and sequences don't move with a rename (the old schema is kept with a note).
- Generated dates don't know about each other unless a CHECK says so (a `RequiredDate` can fall before its `OrderDate`).
- Generating is about 0.4 s per table: every query is followed by a CHECKPOINT (see the decision on the WAL). Fine for a model; a 100-table schema would take a while.
- Filling a table that refers to itself: rows pointing at other rows of the same file pass the check, but DuckDB rejects them in one INSERT; the insert then fails as a whole with DuckDB's message (nothing written).
- Reloading or removing a dataset loses changes made to its tables (the app asks first).

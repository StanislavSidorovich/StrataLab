## Where we are (2026-10-17, interface buttons P2: tree search, result and tab menus, database backup)

**The second round of buttons from the comparison with SSMS, DBeaver and Azure Data Studio** (priority P2 in the project's notes):

- **Find a table or column**: a search box over the tree (Esc clears it) keeps the tables whose name, `schema.name` or one of whose columns contains what was typed; a table found by a column opens on it, the match is marked, dataset folders and the POSTGRESQL section are filtered too, the counts read `TABLES (1/4)`. A **Refresh** button next to it reads both databases again (`src/core/tree.ts`).
- **Result bar**: **Copy ▾** (with or without headers), **Export ▾** (CSV, Excel, **JSON**, **Parquet**) and **Save as table** (asks for a name, the tab's title by default, and before replacing a table). A right-click (a long press on a phone) on a cell copies that value, its row, its column or the whole result. JSON is an array of objects, one row per line, numbers and true / false as such, a DECIMAL as a number when nothing is lost (`src/core/jsonWrite.ts`). Parquet and Save as table hand the result in the grid to DuckDB (`insertArrowTable`), so nothing is run again.
- **Tab menu** (right-click or long press on a tab): Rename, Duplicate (next to it, `Query 1 (copy)`), Close, Close others, Close tabs to the right, **Reopen closed tab** (Alt+Shift+T: the browser keeps Ctrl+Shift+T for itself). The last 20 closed tabs with SQL in them are remembered for this visit (`src/core/tabs.ts`).
- **Download database / Restore from a backup** in the ⋯ next to TABLES: the whole DuckDB database (own tables, views, macros, sequences, loaded datasets) as one `quaera-lab-2026-10-17.duckdb`, which opens in DuckDB's own tools (checked with Python's duckdb 1.5.6). Restore replaces everything in one transaction: a file that is not a database leaves the tables as they were. PostgreSQL's tables are not in the backup (`src/db/backup.ts`, `src/core/backup.ts`).
- **Keyboard shortcuts** listed in the guide (? button), with ⌘ on a Mac.

How it was checked: 91 unit tests green (17 new, `tests/workbench.test.ts`). In Chromium with Playwright, dev server and production build, light and dark, desktop and 390 px (no page scroll; the result bar's buttons become icons): search by name, by column and with no match; JSON downloaded with numbers, booleans and ISO dates; Copy without headers, Copy value from the cell menu; Save as table → `top3` in the tree and queryable; Duplicate, Close others, Alt+Shift+T; backup downloaded, tables dropped and changed, restore brought back exactly the backup (a second schema with foreign keys, a view, a macro, a sequence), and it was still there after a reload; a broken file was refused with the tables untouched; the tab menu opened by a long touch. **Not tried:** Parquet export of a result (needs the Parquet extension from extensions.duckdb.org, blocked in this session: the export shows DuckDB's error), a real phone. ### Earlier (2026-10-17, stage 4 done: dialects; welcome screen)

**Stage 4 done: each query tab speaks DuckDB, SQL Server (T-SQL) or PostgreSQL.** A switch above the editor (DuckDB · SQL Server (T-SQL) · PostgreSQL) is kept per tab.

- **T-SQL → DuckDB.** A T-SQL tab is translated before it runs: sqlglot 30.23 in Pyodide (Python in WebAssembly) in a Web Worker, `src/dialects/translate.py`. The result pane gets a **T-SQL → DuckDB (n)** view: each statement as written next to the DuckDB SQL that ran, what was taken out struck through in red, what came in green (`src/core/diff.ts`, a word diff that ignores case, layout and the `AS` sqlglot adds to aliases), sqlglot's notes under it (“OPTION (…) query hints are SQL Server's own: left out”, variables). **Show translation** translates without running; **Copy DuckDB SQL** / **Open as DuckDB** take the result further. On top of sqlglot: `'a' + name` → `'a' || name`, `BIT` → `BOOLEAN` (DuckDB's BIT is a bit string), `CONVERT(varchar(10), d, 120)` / `CAST(x AS VARCHAR(5))` keep SQL Server's cut to that length (`LEFT(…, 10)`, so the 120 style gives `2026-10-17` as in SSMS), `dbo.orders` → `orders`; scripts are split at `GO`, at semicolons, and between statements written without either (`SELECT @x` newline `SELECT 1`), so each pair lines up. Statements run one at a time and the last result is shown. A DuckDB tab whose query fails with SQL Server habits now offers **Run this tab as T-SQL** under the hints.
- **PostgreSQL.** A PostgreSQL tab runs on PostgreSQL 18.6 (PGlite 0.5.10) in the page, kept in IndexedDB between visits: a separate database from DuckDB, with its own **POSTGRESQL** section in the tree (tables by schema, columns, row counts; select / count / describe / drop) and completion of its tables. **Copy to PostgreSQL** (a table's ⋯ menu, a dataset folder's menu, or **Copy my tables here** in the bar) recreates the tables with their primary keys, UNIQUEs and CHECKs, copies the rows (DuckDB writes CSV, PostgreSQL's `COPY` reads it), then adds the foreign keys; the user's tables go to `public`, a dataset keeps its schema (`chinook."Track"` is the same query in both engines). Results use the same grid, copy and exports, with PostgreSQL's type names in the header (integer, numeric, text…). Errors read “PostgreSQL Error: …” with PostgreSQL's hint.
- Both engines are served with the site (`pyodide/` copied from the npm package at build time by `vite.config.ts`, the sqlglot wheel in `public/sqlglot/`, PGlite in `assets/`) and downloaded only when a tab switches dialect: ~12 MB for the translator, ~10 MB for PostgreSQL, once. The first chunk grew 314 → 329 kB (gzip).

**Welcome screen.** On a first visit (not when arriving with `#ddl=` or `#ds=`), a dialog says what Quaera Lab is, offers three starts (try the demo shop · load a sample database · bring your own file) and says where things are (object tree, query tabs and dialects, result and messages, the engine badge); the **?** button in the header opens it again. The demo shop's four tables carry a **demo** tag, with a line saying they are made-up practice data and a **Remove** link.

How it was checked: 68 unit tests green; the new ones run the real translator (Pyodide + sqlglot in Node, as in the worker: TOP, brackets, ISNULL, GETDATE, DATEADD, IIF, CONVERT with style 120, text +, BIT, dbo, GO / semicolon / no-separator splitting, notes, errors), the word diff, the copy plan and PostgreSQL results as Arrow. ## Decisions

- ✱ **Engine: DuckDB-WASM** (MIT) rather than SQLite (too weak) or PGlite (kept for stage 4 as a dialect). Reads CSV/Parquet/JSON natively, fast on millions of rows.
- ✱ **No server.** Static site on GitHub Pages; the user's data never leaves the browser (no GDPR question, zero hosting cost).
- ✱ **OPFS registered by hand** (`src/db/engine.ts`): DuckDB-WASM 1.33's own `opfs://` path never registers a new, empty database file (it checks `getSize()`), so everything silently stayed in memory while the UI said “saved”. We create both files (`.duckdb`, `.wal`) and register them under plain names. A second tab cannot lock the same file, so it falls back to an in-memory database and the badge says so.
- ✱ **Excel via SheetJS CE 0.20.3** from cdn.sheetjs.com (the npm `xlsx` package is stuck on a vulnerable 0.18). Sheets are written to CSV with ISO dates, then DuckDB sniffs the types, so CSV and Excel go through one path.
- ✱ **Detection before DuckDB's sniffer** (`src/core/sniff.ts`): Windows-1251 fallback when the file is not valid UTF-8, `;` delimiter, decimal comma, `dd.mm.yyyy` dates. DuckDB can't do encodings and needs `decimal_separator` / `dateformat` to be told.
- ✱ **F5 runs the query** (SSMS habit) anywhere on the page, instead of reloading it.
- ✱ **T-SQL hints, not silent rewriting** (`src/core/dialect.ts`): when a query fails, SQL Server habits (`TOP`, `[brackets]`, `ISNULL`, `GETDATE()`, `GO`…) get a “use this instead” note. Seeing the difference is part of learning.
- ✱ **English UI**, like StrataSQL and StrataFlow (international students); RU/PT in stage 6.
- ✱ **Demo shop on first visit** (4 tables, fixed seed) so the welcome query works before any file is dropped.
- ✱ **`#ddl=` packing = StrataSQL's share links** (UTF-8 → deflate-raw → base64url, no padding), via the browser's own CompressionStream: no library, and one format across the Quaera apps. A link that inflates past 5 MB is refused (read chunk by chunk, so a crafted link can't fill the memory).
- ✱ **Foreign keys folded into CREATE TABLE** (`src/core/ddlPlan.ts`): StrataSQL (like pg_dump) adds FKs with `ALTER TABLE … ADD CONSTRAINT`, which DuckDB doesn't support. The plan moves each FK into its table and orders tables so referenced ones come first; a circle of tables loses the FK that closes it, with a note. Self-references are kept.
- ✱ **Translate what is safe, report the rest**: `public.` dropped, `serial` → integer NOT NULL, `GENERATED … AS IDENTITY`, `ON DELETE CASCADE / SET NULL`, `DEFERRABLE` and storage options left out with a note; names that are keywords only in DuckDB (`at`, `map`, `pivot`…) quoted; `DROP TABLE` never run (we ask instead). If DuckDB still rejects a table, it is retried without its FKs, then without its CHECKs, and the dialog says which.
- ✱ **Ask before replacing**: replace all / keep the existing ones and create the rest / cancel. Drops go in reverse creation order; a table another (non-model) table still refers to is kept, with a note.
- ✱ **No demo shop when arriving with a model**: whoever came from model.quaera.app came for that model, and the demo's `customers` / `orders` could clash with it.
- ✱ **One StrataLab tab**: StrataSQL's link opens a named window (`stratalab`), and StrataLab also reads `#ddl=` on `hashchange`, so a second click lands in the same tab (a second tab could not lock the saved database and would fall back to memory).
- ✱ **We download DuckDB's .wasm ourselves** (`src/db/engine.ts`) and hand DuckDB a `blob:` URL, counting bytes on the way. DuckDB's own progress callback only fires when chunks arrive more than 20 ms apart, so on a decent connection it stays silent. The file comes gzip-compressed, so Content-Length is useless for a percentage; `vite.config.ts` puts the unpacked sizes of both .wasm builds into the bundle at build time (`__DUCKDB_WASM_BYTES__`). The bar stops at 99% until the engine has started.
- ✱ **Check everything, then insert** (stage 2b, `src/core/fill.ts`): the file is copied into a temp table and each rule is one SQL query over a view that casts every column to the table's type, so a big file is checked by DuckDB, not row by row in JavaScript. The report lists rows by the number the user sees in the file.
- ✱ **Insert the good rows, skip the bad ones** rather than all-or-nothing (SSMS's import fails as a whole): the button says how many go in and how many are left out. Of two rows with the same key, the first is kept.
- ✱ **A file named like an empty table fills it** (a modelled table waiting for data); a table with rows is only filled when chosen (dropped onto, menu, or the dialog's select).
- ✱ **No silent rounding**: a fractional number going into an integer column is a problem. A decimal-comma file whose number column became text (one stray value) is still read with the comma, spaces as thousands separators.
- ✱ **One schema per dataset** (`chinook.Track`): datasets never clash with each other (Chinook and Sakila both have `customer`) or with the user's tables, and `schema.table` reads like SQL Server's `dbo.`. The user's own tables stay in `main`, unqualified.
- ✱ **Datasets served with the site** (GitHub Pages, `public/datasets/`), not a separate CDN: 2.3 MB of Parquet, same origin, no CORS question. **Original table and column names** kept (Chinook's PascalCase, Northwind's `"Order Details"`) so tutorials' queries carry over.
- ✱ **Built offline by `scripts/build-datasets.py`** with the browser's DuckDB version (1.5.4): Northwind from Microsoft's T-SQL script (m/d/yyyy dates → DATE, money → DECIMAL(10,2) checked for lost cents, pictures left out), Chinook / Sakila / Quaera from SQLite (Quaera's ISO-text dates → DATE). Sakila's `store.manager_staff_id` FK is left out: it closes a circle with `staff.store_id`, and DuckDB can't add a key later.
- ✱ **Self-referencing tables load in rounds** (bosses first): DuckDB checks a foreign key against rows already in the table, not rows of the same INSERT.
- ✱ **A dataset load is not one transaction**: after a dataset was dropped from a reopened file, DuckDB 1.5 refuses to commit several CREATE TABLEs with foreign keys together (“subject … has been deleted”). One statement at a time works; a failed load drops its schema again.
- ✱ **WAL emptied on start, CHECKPOINT after every query** (`src/db/engine.ts`), see “Where we are”. A crash between a write and its checkpoint loses that one write; a stale WAL lost the whole database.
- ✱ **AdventureWorks = AdventureWorksLT** (the `SalesLT` schema, 10 tables), not the full OLTP database (~70 tables in 5 schemas, 20+ MB): it is the one Azure SQL and most short tutorials use, and it fits the catalog's size. Built from Microsoft's own `AdventureWorksLT2022.bak` restored into SQL Server (any instance reachable by `sqlcmd`; Docker works), read back with `FOR JSON` as text and cached in `data-local/datasets-src/adventureworkslt/`, so later builds need no server. The OLTP CSVs were the other route, but they hold the full database, not LT's rows.
- ✱ **AdventureWorks types**: money → DECIMAL(19,4) (416 of 542 unit prices have 3–4 decimals, so (10,2) would lose them); `OrderDate`, `DueDate`, `ShipDate`, `SellStartDate`, `SellEndDate`, `DiscontinuedDate` → DATE (never a time of day, checked by the build); `ModifiedDate` → TIMESTAMP (some have one); `uniqueidentifier` → UUID; `tinyint` → SMALLINT; `bit` → BOOLEAN; the `xml` column as text; `ThumbNailPhoto` left out; the three views left out (one parses XML, one is a recursive CTE that is a good exercise to write).
- ✱ **Computed columns stored as values** (`LineTotal`, `SalesOrderNumber`, `TotalDue`): DuckDB's generated columns can't be filled by `INSERT … BY NAME` and would surprise the fill and DDL features; the values are SQL Server's own. `ON DELETE CASCADE` (order lines) left out, like StrataSQL's models.
- ✱ **Defaults that need nothing extra**: `rowguid` defaults to `uuid()`, `ModifiedDate` to `CAST(now() AS TIMESTAMP)`, `OrderDate` to today via `now()`, so an INSERT can leave them out as in SQL Server. `localtimestamp` and `current_date` were avoided: in DuckDB-WASM they first download the ICU extension.
- ✱ **Kept as in the source**: the Arabic, Hebrew, Thai and Chinese product descriptions are question marks in Microsoft's backup itself (508 of 762); they are not repaired, the card says so.
- ✱ **“Show as model” sends PostgreSQL-flavoured DDL in `#sql=`** (same packing as `#ddl=`), not a model file: StrataSQL already turns SQL into a model (#32) with its own rules (intermediate entities, roles, dependent entities), so the link carries only what the database knows. Types are renamed to what StrataSQL reads; a type with no column type in a model (LIST, STRUCT…) goes as text with a note in Messages; a foreign key to a table in another schema is left out with a note.
- ✱ **One schema per click**: the user's own tables (`main`) from the TABLES header, a dataset from its folder's menu. Mixing them would put two unrelated databases in one model.
- ✱ **Named window both ways**: StrataLab opens `stratasql`, StrataSQL names its tab `stratasql`, as StrataSQL → StrataLab already uses `stratalab`. The window is opened synchronously on the click, then pointed at the link: a window opened after an await may be blocked.
- ✱ **Demo shop with keys** (see “Where we are”): it is the first thing a learner shows as a model, and the comment already promised keys.
- ✱ **Generated inside DuckDB, not in JavaScript**: each table is one `CREATE TEMP TABLE … AS SELECT … FROM range(n)` plus one filtered INSERT, so 10,000 rows cost the same as 100 and the same rules (CHECK, keys) that guard the table pick the rows. The CHECK text DuckDB keeps is reused as the filter, so any CHECK holds, not only the ones we read hints from.
- ✱ **Plausible over random**: a column called email gets `user17@example.com`, first_name a first name, city a city, a code-like key `CUSTOMER-00017`; other text is “Column name 17”, so a learner can see which row is which. Dates fall in 2023–2025. No NULLs except a nullable foreign key with no parent yet (a key to itself on the first fill).
- ✱ **Never more than asked, sometimes fewer**: when the keys leave too few combinations (a junction table over 5 × 5 rows) the dialog says how many went in and why the rest did not.
- ✱ **Dialect per tab, not per app** (stage 4): a learner compares the same query in DuckDB, T-SQL and PostgreSQL in neighbouring tabs. Tabs saved before stage 4 stay DuckDB.
- ✱ **T-SQL is translated, then run on DuckDB** (no SQL Server in a browser, SPEC §7): the side-by-side view is the lesson. **sqlglot in Pyodide** rather than a JavaScript translator: sqlglot is the maintained T-SQL → DuckDB translator; Python costs a ~12 MB download, once, in a worker, only for T-SQL tabs.
- ✱ **Pyodide, sqlglot and PGlite served with the site**, not from a CDN: same origin, works where a network blocks CDNs (this cloud session blocks cdn.jsdelivr.net), and ready for the offline PWA of stage 6. sqlglot is the PyPI wheel as is (`public/sqlglot/`), unpacked into Pyodide (no micropip, no index). Pyodide is MPL-2.0 (file-level copyleft): served unmodified, licence and source named in `public/sqlglot/NOTICE.md`.
- ✱ **Fixes on top of sqlglot where it keeps T-SQL's text but DuckDB reads it differently** (`'a' + b`, `BIT`, `VARCHAR(n)` in CAST / CONVERT, `dbo.`), each with a test; sqlglot's warnings become notes in plain words. `NULLS FIRST` that sqlglot adds to ORDER BY is kept: SQL Server does sort NULLs first, and the diff shows it.
- ✱ **Word diff, not line diff**: sqlglot re-indents, so lines never match; words compared without case show what really changed. The `AS` sqlglot adds before every alias is not counted as a change.
- ✱ **PostgreSQL = PGlite** (Apache-2.0, PostgreSQL 18), a separate database in IndexedDB (`idb://quaera-lab-postgres`) rather than a view over DuckDB's tables: it is the real engine, so its errors, types and functions are PostgreSQL's own. Tables get there by an explicit copy; the copy replaces tables with the same names (`DROP … CASCADE`) and adds foreign keys after the rows, so table order and circles of keys don't matter.
- ✱ **`main` → `public`, a dataset keeps its schema name** in PostgreSQL, so queries move between the two engines unchanged.
- ✱ **PostgreSQL results as Arrow** (`src/dialects/pgResult.ts`): one grid, copy and export path for both engines; bigint read as BigInt (no silent rounding past 2^53); the header shows PostgreSQL's type name; duplicate column names become `id`, `id_2`.
- ✱ **PGlite without `relaxedDurability`**: with it, starting on an IndexedDB store raised an uncaught `ErrnoError` in Chromium.
- ✱ **Welcome screen once**, then behind the ? button; not shown to someone arriving from model.quaera.app or a `#ds=` link (they came for that). The demo shop stays the default first query, now labelled as made-up data.
- ✱ **PWA: the shell up front, the engines on first use** (`src/core/pwa.ts`). The build is ~110 MB (DuckDB's eh and mvp .wasm ~75 MB, Pyodide ~13 MB, PGlite ~17 MB, datasets), and a visit uses one DuckDB build and maybe none of the rest, so precaching every file as StrataFlow does would mean 110 MB on a first visit. Install caches the page, scripts and styles (~5 MB); `.wasm`, `.data`, `pyodide/`, `sqlglot/` and `datasets/` are cached when first fetched, keyed by content hash in a cache that survives deploys, so an unchanged engine is not downloaded again and a changed one (Pyodide files keep their names) is. Range requests and other sites (extensions.duckdb.org) are not touched.
- ✱ **Update waits for a click** (no `skipWaiting` on install), as in StrataFlow: an open tab may still lazy-load its own version's chunks (the translator, PGlite).
- ✱ **Install as app sits in the guide** (? button): StrataLab has no Help menu.
- ✱ **Stop by DuckDB's own cancel, not by killing the worker**: restarting the worker would cost the 2 s start and any unsaved write. The price: in a DuckDB script, the statements before the last run in one go when it starts and can't be stopped midway (T-SQL tabs run statement by statement, so every one can).
- ✱ **Format makes keywords upper case** (`SELECT`, `FROM`), the usual SSMS / textbook look; names and functions are left as written. One Undo step.
- ✱ **Pasted text becomes a table only outside the editor**, and only when it looks like one (two lines with the same number of tabs); inside the editor Ctrl+V pastes text as always.
- ✱ **Save without a picker downloads**, named after the tab (`Query 1.sql`); with a picker, the file a tab came from is remembered for this visit only.
- ✱ **Backup = a .duckdb file, not a zip of Parquet** (`EXPORT DATABASE`): one file that DuckDB, Python and DBeaver open as is, no zip library, and Parquet export needs an extension from the network. Made by attaching a new file and `COPY FROM DATABASE … (SCHEMA)`, then filling the tables parents first: DuckDB's own copy of the rows goes alphabetically and fails on foreign keys (order_items before orders). - ✱ **Restore replaces, it does not merge**: two databases with the same table names have no right merge; the app asks first and says to download a backup before. All in one transaction.

## Known gaps

- Reading Parquet (the datasets, dropped .parquet files) makes DuckDB-WASM download its Parquet extension from extensions.duckdb.org on first use (and the ICU extension for `current_date`, time zones…). A network that blocks that host breaks dataset loading. Serving the extensions with the site (`custom_extension_repository`) would also make datasets load offline (the PWA caches everything else, 2026-10-17).

- Numbers with a space as thousands separator (`1 234,50`) stay text: DuckDB has no thousands option. Could be cleaned before import.
- A query result is held in memory in full; `SELECT *` on tens of millions of rows will be slow. A row cap with “show more” is a candidate.
- A multi-statement script in a DuckDB tab runs its statements before the last in one go: Stop only interrupts the last one. Running DuckDB tabs statement by statement needs a splitter (DuckDB-WASM's `extractStatements` is a candidate).
- PostgreSQL tabs have no Stop (PGlite can't cancel a query).
- The database backup has DuckDB's tables only; PostgreSQL's (PGlite) are not in it.
- A tab opened from a .sql file forgets the file on reload: the next Save asks where to save again.
- T-SQL that has no DuckDB counterpart is passed on and fails in DuckDB with DuckDB's error: variables (`DECLARE @x`), `MERGE … OUTPUT inserted.…`, `BEGIN TRY … END CATCH`. The translation view says so where sqlglot warns; `EXEC` (stored procedures) is stopped before running with a note. `SELECT … INTO #tmp` works (a temporary table).
- `'text' + column` is turned into `||` only when one side is a string literal (or already a `||`): `first_name + last_name` stays `+` and fails in DuckDB with the T-SQL hint. sqlglot doesn't know column types.
- The PostgreSQL database is one per browser (IndexedDB) and not locked: two tabs of Quaera Lab writing to PostgreSQL at once could overwrite each other's changes. PostgreSQL's data is separate from DuckDB's: a change in one is not seen in the other until copied again (the copy replaces).
- Copying to PostgreSQL: `LIST` / `STRUCT` / `MAP` columns go as text; DuckDB CHECKs PostgreSQL rejects are left out with a note (none in the catalog datasets were seen to fail, but not all were tried, see above).
- Not tried yet on Safari / Firefox (OPFS sync access handles are supported there, but untested).
- `#ddl=` opened while StrataLab is already open in a tab **not** started from StrataSQL's link (typed address, bookmark) opens a second tab, which gets an in-memory database (the badge says so).
- “Show as model” sends the current state of the tables: the model is a new copy in StrataSQL, not linked back (edits there don't come back to StrataLab; StrataSQL's “Open in StrataLab ↗” does that way).
- DuckDB foreign keys only block: `ON DELETE CASCADE / SET NULL` from a model are left out (noted in the dialog).
- Mobile: usable to look, not to work (sidebar hidden below 768 px; the catalog has a header button).
- Filling works only into the user's own tables (schema `main`), not into a dataset's.
- Generated dates don't know about each other unless a CHECK says so (a `RequiredDate` can fall before its `OrderDate`).
- Generating is about 0.4 s per table: every query is followed by a CHECKPOINT (see the decision on the WAL). Fine for a model; a 100-table schema would take a while.
- Filling a table that refers to itself: rows pointing at other rows of the same file pass the check, but DuckDB rejects them in one INSERT; the insert then fails as a whole with DuckDB's message (nothing written).
- Reloading or removing a dataset loses changes made to its tables (the app asks first).
